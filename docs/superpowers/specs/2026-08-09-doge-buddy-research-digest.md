## cj-api

> **[2026-08-23]** "VERIFIED" in this section means *verified against CJ's docs* — the live wire format diverges in several places (required `platform`, `shipping*` address names, null `shipmentOrderId`/`orderAmount` on createOrderV3, `orderNum` vs `orderNumber`, dispute shapes, `isSandbox: 1` as the only honored sandbox flag, API-key UI moved behind Apps → Install App, `openId` only via `GET /setting/get`). The webhook signature scheme remains doc-only — no live CJ webhook observed yet. **`docs/cj-api-notes.md` supersedes this section wherever they disagree.**
CJ Dropshipping's API 2.0 (base https://developers.cjdropshipping.com/api2.0/v1, JSON over HTTPS, CJ-Access-Token header) covers everything the ops service needs: token auth with 15-day access / 180-day refresh tokens, product search with US-warehouse and trending filters, full variant/stock/freight data, programmatic order creation and wallet-balance payment, tracking retrieval, webhooks for order/logistics/stock/product events, a sourcing-request flow, and a dispute (refund/reissue) API. Rate limiting is tier-based QPS (1 req/s on a Free account) plus a 50,000-points/day quota; product list calls cost 50 points, most others 10 or 0. The main operational gaps: wallet top-up itself is not exposed via API (manual recharge required), and account-tier QPS makes bulk catalog syncing slow on the free tier.

Key facts:
- VERIFIED (auth): POST /api2.0/v1/authentication/getAccessToken with body {apiKey} (format CJUserNum@api@[key]) returns accessToken (expires 15 days), refreshToken (expires 180 days), openId, expiry dates. POST /api2.0/v1/authentication/refreshAccessToken with {refreshToken} renews both. POST /api2.0/v1/authentication/logout (header CJ-Access-Token) invalidates both immediately. getAccessToken is limited to 1 call/second and is server-cached: repeat calls within 24h return the SAME token pair.
- VERIFIED (auth setup): API key is generated in the dashboard at cjdropshipping.com > My CJ > Authorization > API > API Key. All API 2.0 requests use header CJ-Access-Token plus Content-Type: application/json; response envelope is {code, result, message, data, requestId}.
- VERIFIED (product discovery): GET /api2.0/v1/product/listV2 — params keyWord, page (1-1000), size (1-100), categoryId, countryCode (e.g. 'US' — filters to products WITH INVENTORY in that country, exactly what we need for US-warehouse filtering), startSellPrice/endSellPrice, productType (4=supplier, 10=video, 11=non-video), orderBy (0=best match, 1=listing count, 2=sell price, 3=create time, 4=inventory), sort (asc/desc), productFlag (0=Trending, 1=New, 2=Video, 3=Slow-moving), verifiedWarehouse (1=verified inventory), features array (enable_description, enable_category, enable_combine, enable_video). Older GET /api2.0/v1/product/list also exists (50 points/call each). GET /api2.0/v1/product/getCategory returns the 3-level category tree; GET /api2.0/v1/product/globalWarehouseList enumerates warehouses/areas.
- VERIFIED (product detail): GET /api2.0/v1/product/query (by pid, productSku, or variantSku; countryCode; features) returns full product incl. variants, weights, dimensions, materials, packaging, logistics properties. GET /api2.0/v1/product/variant/query (all variants by pid/sku), GET /api2.0/v1/product/variant/queryByVid (features=enable_inventory adds warehouse-level stock). Stock: GET /api2.0/v1/product/stock/queryByVid, /product/stock/queryBySku, /product/stock/getInventoryByPid — all return per-warehouse inventory (CJ-managed vs factory, verified/unverified). Reviews: GET /api2.0/v1/product/productComments. Videos: POST /api2.0/v1/product/queryVideosByProductId. Image search: /product/queryProductsByImage (costs 1,000 points/call).
- VERIFIED (shipping cost): POST /api2.0/v1/logistic/freightCalculate — body {startCountryCode, endCountryCode, products:[{vid, quantity}], zip…} returns per-option logisticName, logisticPrice (USD), logisticAging (delivery days). Advanced: POST /api2.0/v1/logistic/freightCalculateTip (weight/volume/sku-level, returns postage, arrivalTime, discountFee, remoteFee, taxesFee, totalPostageFee, channel/option IDs). POST /api2.0/v1/logistic/partnerFreightCalculate quotes against a full shipping address. Tracking: GET /api2.0/v1/logistic/trackInfo?trackNumber=… (batch-capable; returns trackingStatus, logisticName, deliveryDay, lastMileCarrier, lastTrackNumber). /logistic/getTrackInfo is deprecated.
- VERIFIED (order lifecycle): POST /api2.0/v1/shopping/order/createOrderV2 (and V3, recommended: adds shopLogisticsType 1=platform/2=merchant/3=platform+CJ warehouse and storageId) — key params orderNumber, shippingCountryCode, fromCountryCode, logisticName, products:[{vid|sku, quantity}], and payType: 1=pay via CJ page (returns cjPayUrl), 2=PAY DIRECTLY FROM WALLET BALANCE at creation, 3=create only. Response: orderId, shipmentOrderId, orderAmount, productAmount, postageAmount. Status flow: CREATED / IN_CART -> UNPAID -> UNSHIPPED (sub-statuses PENDING 300-399, PROCESSING 400-499) -> SHIPPED -> DELIVERED; plus CANCELLED. PATCH /shopping/order/confirmOrder, DELETE /shopping/order/deleteOrder (only CREATED/IN_CART), GET /shopping/order/list (status, orderIds, paymentDate range max 90 days), GET /shopping/order/getOrderDetail (features=LOGISTICS_TIMELINESS; includes tracking info), POST /shopping/order/getOrderDetailBatch (up to 100). Logistics on an existing order: GET /shopping/order/getOrderLogisticsInfo, POST /shopping/order/updateLogistics.
- VERIFIED (payment): GET /api2.0/v1/shopping/pay/getBalance returns {amount, noWithdrawalAmount, freezeAmount}. POST /api2.0/v1/shopping/pay/payBalance {orderId} and POST /shopping/pay/payBalanceV2 {shipmentOrderId, payId} deduct from CJ wallet programmatically; error code 1600100 = insufficient balance. So fulfillment CAN be fully programmatic: createOrderV3 -> confirmOrder -> payBalanceV2 (or createOrder with payType=2). No wallet-recharge/top-up endpoint exists anywhere in the API docs — funding the wallet is a manual dashboard action.
- VERIFIED (sandbox): createOrderV2/V3 accept a sandbox flag; sandbox helpers exist: POST /api2.0/v1/shopping/sandbox/simulatePay, POST /shopping/sandbox/updateStatus (targetStatus 400/500/600/700, must flow 300->400->500->600->700 without skipping), POST /shopping/sandbox/updateTrackNumber — enough to integration-test the whole fulfillment pipeline without spending money.
- VERIFIED (webhooks): POST /api2.0/v1/webhook/set configures topics {product, stock, order, logistics, makeup, privateOrder} each with type ENABLE/CANCEL + callbackUrls (HTTPS, TLS 1.2+, must respond within 3 seconds). Event types: PRODUCT (INSERT/UPDATE), STOCK, ORDER (creation/status updates), LOGISTICS (tracking updates), MAKEUP bills, PRIVATE_ORDER. Product/stock webhooks require subscribing products: POST /webhook/product/subscribe (max 100 ids/call; total cap by tier, lv1=100 up to lv5=10,000), /webhook/product/unsubscribe, GET /webhook/product/subscribe/list. Payload signature: sign = Base64(HmacSHA256(secret=openId, message=raw body)). Delivery retried up to 3x; webhook auto-disabled if success rate <80% over 2 hourly windows.
- VERIFIED (rate limits): max 10 req/s per IP; 30 req/s for non-login interfaces; max 3 CJ users per IP. Per-account QPS by tier: Free/level 0-1 = 1 req/s, Plus/2 = 2, Prime/3 = 4, Advanced/4-5 = 6. Daily quota is points-based (old daily-call limits deprecated): every user gets 50,000 base points/day (reset 00:00 UTC, replenished per-minute at total/1440) plus bonus points = max of last 3 months' transaction amount x 100 ($1 = 100 pts). Costs: /product/listV2 and /product/list = 50 pts, /product/queryProductsByImage = 1,000 pts, most other listed endpoints = 10 pts, unlisted endpoints = 0. Exhaustion returns HTTP 429 with code 429 and a pointsInfo object.
- VERIFIED (sourcing requests): POST /api2.0/v1/product/sourcing/create — params productName, productImage (URL), optional third-party product IDs and target pricing; returns a CJ sourcing id. POST /api2.0/v1/product/sourcing/query with {sourceIds:[…]} returns sourcing status and, when fulfilled, the matched CJ productId/variantId. This is the official 'source a product not in the catalog' flow.
- VERIFIED (disputes/refunds): flow is GET /api2.0/v1/disputes/disputeProducts?orderId= (which line items are disputable) -> POST /disputes/disputeConfirmInfo (returns max refundable amounts, allowed expectResultOption 1=Refund/2=Reissue, and valid disputeReasonList) -> POST /disputes/create {orderId, businessDisputeId (your unique idempotency id), disputeReasonId, expectType 1=Refund/2=Reissue, refundType 1=balance/2=platform, messageText, imageUrl[], videoUrl[], productInfoList}. Also POST /disputes/cancel, GET /disputes/getDisputeList, GET /disputes/getDisputeDetail (finallyDeal: 1=Refund, 2=Reissue, 3=Reject; refundDetails typed PRODUCT_COST/SHIPPING_COST/IOSS_TAX/IOSS_HANDLING_FEE). Refunds go to your CJ wallet or platform — refunding the end customer on Shopify remains our own job.
- VERIFIED (other): GET /api2.0/v1/setting/get (account settings), GET /api2.0/v1/warehouse/detail (warehouse info), POST /shopping/order/getProofOfDelivery (up to 100 orderIds). OAuth-style endpoints exist for multi-tenant apps (/authentication/getAuthorizeUrl, /authentication/exchangeAccessToken) — not needed for our single-account service.
- UNVERIFIED (recollection, consistent with docs' silence): CJ wallet can be topped up via PayPal, card, wire, or crypto in the dashboard, and CJ can auto-deduct... no auto-recharge API was found, so treat wallet funding as manual. Also UNVERIFIED: exact dispute time window (commonly cited as within ~30 days of delivery) — confirm in the CJ dashboard/user agreement before building the support agent's refund logic.
- VERIFIED (docs meta): official docs live at developers.cjdropshipping.com (mirrored at developers.cjdropshipping.cn); docs are organized as API 2.0 modules: Authentication, Setting, Product, Storage, Shopping, Logistic, Dispute, Webhook, Shop. The docs explicitly advise AI-assisted developers to refresh their local knowledge of the API monthly because interfaces change.

Gotchas:
- Free-tier QPS is 1 request/second per account — the ops service MUST funnel every CJ call through a single global rate-limited client (token bucket, 1 rps, with 429/limit-error backoff). Initial catalog sync of thousands of products will be slow by design; the sourcing agent should page listV2 lazily, not mirror the whole catalog.
- Points quota: product list/search calls cost 50 points each (max ~1,000 list calls/day within the 50k base quota, shared with everything else) and points replenish per-minute (total/1440), so a burst crawl early in the day will starve fulfillment calls. Budget points per workflow; image search (1,000 pts) is effectively off-limits for routine use.
- getAccessToken is cached server-side for 24h and limited to 1 call/sec — never fetch a token per request. Store the token pair in Postgres, reuse for ~15 days, refresh via refreshAccessToken before expiry, and treat logout as a token-rotation tool.
- No API endpoint tops up the CJ wallet. payBalance/payBalanceV2 fail with code 1600100 when balance is insufficient, which would silently stall auto-fulfillment. Build a balance monitor (getBalance) with an alert threshold and an owner-facing 'wallet low' notification; the per-order spend cap should also check current balance.
- Order tracking numbers are NOT returned at order creation — they appear later (order reaches SHIPPED). Rely on the LOGISTICS/ORDER webhooks plus a reconciliation poller (getOrderDetail / order list) rather than synchronous polling; note order/list date filters cap at a 90-day window.
- Webhook endpoint must be HTTPS, respond within 3 seconds, and is auto-disabled if success rate drops below 80% over 2 hourly windows — ack immediately and enqueue processing (fits our job-queue design). Verify the HmacSHA256 signature keyed on openId. Product/stock webhooks only fire for explicitly subscribed products (tier-capped: 100 at lv1), so subscribe exactly the SKUs we list.
- Max 3 CJ user accounts per IP — irrelevant for one account, but note if CI and prod share egress IPs with other CJ users on a shared PaaS (Railway/Fly shared IPs could theoretically collide with other CJ API users; if odd 'ip limit' errors appear, get a dedicated egress IP).
- createOrder V1 is legacy; V2/V3 responses and payType semantics differ (V3 adds shopLogisticsType/storageId and is the recommended path). Deleting orders is only possible in CREATED/IN_CART status — after confirm/pay, cancellation goes through the dispute flow.
- US-warehouse filtering (countryCode=US on listV2) filters by inventory presence at search time, but stock is volatile — always re-verify with stock/queryByVid (or variant queryByVid with enable_inventory) and quote freight from fromCountryCode=US at order time; fall back gracefully when US stock is gone (CN shipping times would break customer promises).
- Dispute creation requires a unique businessDisputeId (idempotency key) and only reasons/amounts returned by disputeConfirmInfo are valid — the support agent must call the confirm step first, not hardcode reason IDs. CJ refunds land in the CJ wallet (refundType=1) — Shopify customer refunds are a separate action our service must perform.
- ToS: no separate public API developer agreement was found; API use falls under the general CJ user agreement and store-authorization agreement (data used on a minimum-necessary basis). Nothing found prohibits automation, but the docs warn that interfaces change and recommend refreshing API knowledge monthly — pin against the response envelope (code/result/message/data) and alert on unknown codes.
- Docs are served from both developers.cjdropshipping.com and developers.cjdropshipping.cn; the .com API host (https://developers.cjdropshipping.com/api2.0/v1) is the production base URL — the docs domain doubles as the API domain, which surprises some proxies/allowlists.

Recommendations:
- Build the CJSupplierAdapter around a single shared HTTP client with: token manager (persist accessToken/refreshToken + expiry dates in Postgres, refresh at ~day 13, handle the 24h token cache), a 1-rps token-bucket rate limiter, points-budget tracking, and uniform handling of the {code,result,message,data,requestId} envelope (log requestId on every failure).
- Fulfillment pipeline per locked decision: on Shopify order paid -> freightCalculate (fromCountryCode=US) to pick logistics within margin -> createOrderV3 (shopLogisticsType=1, US storageId, payType=3) -> validate totals against the per-order spend cap -> confirmOrder -> payBalanceV2 -> record shipmentOrderId. Use payType=2 only after the cap check is proven; keeping create and pay as separate steps gives a natural approval/cap gate.
- Use the sandbox flag + /shopping/sandbox/simulatePay + /sandbox/updateStatus + /sandbox/updateTrackNumber to write end-to-end integration tests of the fulfillment worker (including SHIPPED->tracking-sync to Shopify) before spending real money.
- Register webhooks early: webhook/set with order + logistics topics pointed at the ops service (HTTPS endpoint that acks <3s and enqueues), plus stock + product topics with webhook/product/subscribe for every listed SKU. Add a daily reconciliation job (order/list + getOrderDetailBatch) as the safety net for missed webhooks.
- Sourcing agent: use listV2 with productFlag=0 (Trending) / 1 (New), countryCode=US, verifiedWarehouse=1, orderBy=1 (listing count) as the trend signal; enrich winners with product/query + productComments + queryVideosByProductId (videos are great listing assets). Budget roughly <=500 list calls/day (25k points) to leave headroom for fulfillment.
- Support agent refund flow: map customer complaint -> disputeProducts -> disputeConfirmInfo (get valid reasons/amounts) -> draft proposal for owner approval -> disputes/create with businessDisputeId = internal ticket ID, refundType=1 (wallet); poll getDisputeDetail (finallyDeal) and reconcile with the Shopify refund the service issues to the customer.
- Add a wallet-balance monitor job (getBalance every few hours) with alert thresholds (e.g. < 20 expected orders' worth) surfaced in the admin dashboard and owner email, since top-up is manual — this is the single biggest full-auto fulfillment risk.
- Consider CJ Plus/Prime once volume grows: QPS rises (2-4 rps) and 3-month transaction volume automatically grows the daily points quota ($1 spent = 100 bonus points), so quota pressure eases as the store scales.
- Re-verify the docs monthly as CJ itself recommends (a scheduled job or manual check of developers.cjdropshipping.com changelog), and pin adapter tests against recorded fixtures of real responses so interface drift is caught in CI rather than production.

## shopify-admin

> **[2026-08-23]** Client-transfer store created (`doge-buddy-1b9crsev.myshopify.com`); the recommended support confirmation was deliberately skipped, risk accepted.
Researched Shopify platform pieces for the Doge Buddy ops service against the current Admin GraphQL API (latest version 2026-07). Major 2025/2026 platform shifts affect the plan: custom apps can no longer be created in the store admin (new apps are created in the Dev Dashboard and authenticate via a client-credentials grant issuing 24-hour tokens), the new Dev Dashboard "dev store" type cannot be transferred/converted to a live store (the Partner Dashboard "client transfer store" type is the one built for launch handoff), and webhook retries were cut to 8 attempts over ~4 hours with subscription removal on persistent failure. All required mutations, scopes, and webhook topics were confirmed by name, including the 2026-04 mandatory @idempotent directive on refund and inventory mutations.

Key facts:
- VERIFIED: Latest Admin GraphQL API version is 2026-07; quarterly releases, each supported ~12 months. Pin one version and plan quarterly bumps.
- VERIFIED (a): Development stores are now created in the Dev Dashboard (dev.shopify.com/dashboard) with plan tiers Basic/Grow/Advanced/Plus (free, mirror production plan features; early access since May 21, 2025). They cannot process real transactions, the storefront password page cannot be removed, and this new 'dev store' type can't be transferred to a client. The Partner Dashboard 'client transfer store' is the type built for handoff: partner builds it, transfers ownership to a merchant account, the merchant picks a paid plan, all store data persists, and the partner earns 20% recurring revenue share.
- VERIFIED (a): Test checkouts work via the Bogus Gateway or Shopify Payments test mode; gift cards, Store Credit, and manual/POS payment methods cannot be tested. Bogus Gateway transactions must exceed $1 USD equivalent. UNVERIFIED: community reports a ~10-order cap on dev-store test checkouts ('limit for development store orders' error) with no documented number and no official response.
- VERIFIED (b): 'You can no longer create new custom apps in the Shopify admin' — the legacy Settings > Apps > Develop apps flow is closed to new apps (reported cutoff Jan 1, 2026; existing admin-created apps keep working but tokens can only be rotated by uninstall/reinstall). New custom apps are created in the Dev Dashboard or via Shopify CLI, scopes configured in the dashboard or shopify.app.toml.
- VERIFIED (b): Auth for own-org apps on own stores is the client credentials grant: POST https://{shop}.myshopify.com/admin/oauth/access_token with {client_id, client_secret, grant_type: "client_credentials"}; access tokens expire in 86399s (24h, expires_in in response) and are refreshed by repeating the same request. The ops service needs a token-manager with refresh logic — legacy permanent admin tokens are gone for new apps.
- VERIFIED (b) scopes: read_products/write_products (products, variants, product metafields; productSet requires write_products); read_orders/write_orders (orders and refunds — refundCreate doc reads 'Requires orders access scope', i.e. the orders scope family, so grant write_orders); read_all_orders (separate approval required; without it apps only see the last 60 days of orders); fulfillments: fulfillmentCreate requires one of write_assigned_fulfillment_orders / write_merchant_managed_fulfillment_orders / write_third_party_fulfillment_orders (read_fulfillments/write_fulfillments also exist); read_customers/write_customers; read_inventory/write_inventory (inventorySetQuantities requires write_inventory); read_publications/write_publications (publishablePublish requires write_publications); read_files/write_files.
- VERIFIED (b): Protected customer data — custom apps have Level 1 and Level 2 (name/address/email/phone) access 'always available' with no review; apps installed only on development stores are exempt from review entirely; undeclared/unapproved protected fields silently return null with an explanation in the GraphQL errors hash.
- VERIFIED (c) product creation: productCreate (product + initial variant) and productSet (declarative create-or-update sync from an external source: variants with option values, metafields, files via originalSource, status DRAFT/ACTIVE; synchronous by default or async returning ProductSetOperation monitored via productOperation query; 2048-variant default limit). productSet is the intended mutation for supplier-catalog sync. Companion mutations: productVariantsBulkUpdate, productCreateMedia.
- VERIFIED (c) media: stagedUploadsCreate returns stagedTargets {url, resourceUrl, parameters}; POST the file to url with the returned parameters, then use resourceUrl as originalSource in productCreateMedia / fileCreate / productSet files / productUpdate. StagedUploadInput: filename, mimeType, resource (PRODUCT_IMAGE, VIDEO, MODEL_3D, COLLECTION_IMAGE, SHOP_IMAGE...), httpMethod, fileSize (required for VIDEO/MODEL_3D). UNVERIFIED but standard: productCreateMedia/productSet also accept an already-public external image URL directly as originalSource, letting you skip staged uploads for supplier CDN images.
- VERIFIED (c) fulfillment: fulfillmentCreateV2 and fulfillmentTrackingInfoUpdateV2 were deprecated as of API 2024-10; the current mutations are fulfillmentCreate (FulfillmentInput: which FulfillmentOrderLineItems to fulfill, trackingInfo, notifyCustomer) and fulfillmentTrackingInfoUpdate. Flow: query the order's fulfillmentOrders, then fulfillmentCreate against those fulfillment orders.
- VERIFIED (c) refunds: refundCreate with RefundInput {orderId, refundLineItems, transactions, shipping, note, refundMethods (incl. store credit)}. As of API 2026-01 an optional idempotency key via the @idempotent GraphQL directive was added to refund and inventory mutations; as of 2026-04 it is REQUIRED (keys tracked 24h). UNVERIFIED: Order.suggestedRefund query for computing refund amounts (not confirmed on the current docs page).
- VERIFIED (c) inventory: inventorySetQuantities (absolute set; name 'available' or 'on_hand'; compareQuantity compare-and-set, ignoreCompareQuantity to bypass; intended for source-of-truth systems — i.e., the ops service mirroring CJ stock) vs inventoryAdjustQuantities (deltas). Both under the 2026-04 mandatory @idempotent rule.
- VERIFIED (c) publishing: publishablePublish(id: <product GID>, input: [{publicationId}]) requires write_publications. Each Headless/Hydrogen storefront now has its OWN publication — you must publish to the specific storefront's publicationId (query publications to enumerate; GID form gid://shopify/Publication/{id}). Scheduled publishDate only works for the online store channel. ProductVariant is now itself a publishable resource.
- VERIFIED (d) webhook topics (GraphQL enum ↔ topic string): ORDERS_CREATE (orders/create) fires on any order creation including unpaid; ORDERS_PAID (orders/paid) fires when payment is successfully processed — the correct fulfillment trigger; ORDERS_UPDATED, ORDERS_CANCELLED, ORDERS_FULFILLED, ORDERS_PARTIALLY_FULFILLED, ORDERS_EDITED; REFUNDS_CREATE (refunds/create) 'occurs whenever a new refund is created without errors on an order, independent from the movement of money'; FULFILLMENTS_CREATE, FULFILLMENTS_UPDATE; plus FULFILLMENT_ORDERS_* topics.
- VERIFIED (d) webhook mechanics: HTTPS delivery; verify HMAC-SHA256 of the raw request body with the app's client secret against the X-Shopify-Hmac-Sha256 header; no ordering guarantees within or across topics (use X-Shopify-Triggered-At); delivery is not guaranteed — Shopify explicitly instructs apps to run periodic reconciliation jobs polling with updated_at query filters. Subscriptions: declare in shopify.app.toml (recommended, app-owned) or via webhookSubscriptionCreate(topic, webhookSubscription {uri, filter, includeFields, metafieldNamespaces}); payload API version comes from the app's configured webhook API version, not per-subscription.
- VERIFIED (d) retries: since September 2024 failed deliveries are retried 8 times over ~4 hours with exponential backoff (the old 19-retries-over-48h policy is dead), and persistently failing subscriptions are REMOVED — new events silently stop until you re-register. UNVERIFIED recollections: ~5-second response timeout per delivery; X-Shopify-Webhook-Id header for dedup; order payloads carry a test:true flag for Bogus/test-mode orders.
- VERIFIED (e) Shopify Tax US: free until $100,000 USD in sales (calendar-year threshold for stores created before May 13, 2026; LIFETIME cumulative threshold for stores created on/after that date — which applies to a store created now); then 0.35% per US order (0.25% on Plus), capped at $0.99/order; the $5,000/yr regional cap only applies to pre-May-13-2026 stores. Fee applies to orders from regions where tax collection is activated even when zero tax is due; not to regions with collection off or externally imported orders. Rooftop-accurate calculation across 11,000+ jurisdictions and nexus-liability insights are included; registration, filing, and remittance are NOT (filing via Sovos in select states ~$75/return per secondary sources).
- VERIFIED (f): Dropshipping is an explicitly permitted, Shopify-promoted business model. Compliance hinges on the Shopify ToS + Acceptable Use Policy (no counterfeit/IP-infringing goods) and, for Shopify Payments, required published policies: refund/return policy and shipping policy for physical goods, plus a privacy policy that names third-party fulfillment partners (e.g., CJ) that receive customer data. UNVERIFIED (general knowledge): Shopify Payments applies reserves/holds to high-chargeback stores, and FTC Mail Order Rule shipping-time expectations apply to US dropshippers.

Gotchas:
- Store-type trap for the locked 'dev store now, paid at launch' decision: the new Dev Dashboard 'dev store' type explicitly cannot be transferred or launched into production per current docs. The store type designed to become a live paid store is the Partner Dashboard 'client transfer store' (transfer ownership to your own merchant account at launch, then pick a plan). Choosing the wrong type on day 1 could mean rebuilding the store at launch — confirm the convert path with Shopify support before creating the store.
- New custom apps get 24-hour access tokens via client credentials grant — the ops service must implement token caching/refresh (refresh before 86399s expiry). The old permanent admin-token model only survives on custom apps created in the admin before the cutoff.
- Webhook retry window shrank to 8 attempts over ~4 hours (Sept 2024 change), and Shopify silently DELETES persistently failing subscriptions — the ops service needs (1) enqueue-then-ack handler design, (2) a scheduled reconciliation poll of orders by updated_at, and (3) a periodic webhookSubscriptions health check that re-registers missing topics.
- As of API 2026-04 the @idempotent directive (idempotency key) is MANDATORY on refundCreate and inventory adjustment mutations (inventorySetQuantities, inventoryAdjustQuantities, etc.); keys are tracked for 24h. Code written against pre-2026-04 examples will fail.
- productSet is declarative: list fields (variants, collections, metafields per current docs) delete entries omitted from the input — always send the full desired state, never partial lists.
- Without the separately-approved read_all_orders scope, apps only see the last 60 days of orders — affects the scoring agent's historical analysis; request approval early.
- orders/create fires for unpaid orders too — use orders/paid as the auto-purchase trigger, and also check the order's test flag so the fulfillment automation never spends real money at CJ for Bogus/test-mode orders.
- refunds/create fires 'independent of the movement of money' — it signals a refund record was created, not that funds settled.
- New products are not automatically visible on a Hydrogen storefront: each Headless/Hydrogen storefront has its own publication, and the sourcing agent must call publishablePublish with that storefront's publicationId for every new product.
- Protected customer data is 'always available' for custom apps, but it may still need to be configured/declared in the Dev Dashboard; undeclared fields silently return null (HTTP 200 with errors hash), and community threads report UI gaps for enabling it on Dev Dashboard apps.
- Dev store testing limits: no real transactions ever, password page fixed, gift cards/Store Credit/manual payments untestable, and an undocumented (anecdotal ~10) test-order cap has been reported — keep an eye on it during fulfillment-pipeline testing.
- Shopify Tax threshold semantics changed May 13, 2026: new stores get a LIFETIME $100k free threshold (not per-calendar-year), after which every taxed US order costs 0.35% up to $0.99 — model this into unit economics.
- Apparel pipeline (future): AUP/IP compliance matters most here — AI-generated designs referencing brands/characters risk counterfeit/IP takedowns, a known store-termination trigger.

Recommendations:
- Create the build store as a Partner Dashboard client transfer store (not a Dev Dashboard dev store) so the launch path is: transfer ownership to the Closing Brackets LLC merchant account -> pick a paid plan -> same store, all data intact. ## gmail
Programmatic Gmail for the support agent is best built as: a dedicated Google Workspace user for support@ (not a Group or alias — neither has an API-accessible mailbox of its own), authenticated headlessly either via a service account with domain-wide delegation (most durable; no consent flow, immune to password-change token revocation) or via an Internal-user-type OAuth app whose refresh tokens do not expire on the 7-day testing rule. For receiving, users.watch + Pub/Sub push works but expires silently after 7 days and needs a daily renewal cron; simple users.history.list polling every 30–60s costs only 2 quota units per call and fits easily inside the 6,000 units/min/user quota, making it the simpler day-one choice for the always-on ops service. Threading requires threadId in the send request plus matching Subject and RFC 2822 In-Reply-To/References headers; labels (users.labels.create + users.messages.modify) work well as a human-visible mirror of ticket state; deliverability needs SPF (include:_spf.google.com), a 2048-bit DKIM key activated in Admin console, and a DMARC record starting at p=none.

Key facts:
- VERIFIED (developers.google.com/workspace/gmail/api/guides/push): Gmail push = create Pub/Sub topic; grant the Publisher role on that topic to gmail-api-push@system.gserviceaccount.com; create a push (HTTPS webhook) or pull subscription; call users.watch with {topicName, labelIds:["INBOX"], labelFilterBehavior:"INCLUDE"}. Watch must be re-called at least every 7 days; docs recommend calling it once per day. Notification payload is base64url JSON {emailAddress, historyId}; on receipt call users.history.list with startHistoryId = your last stored historyId.
- VERIFIED (developers.google.com/workspace/gmail/api/reference/quota, current Aug 2026): Gmail API quotas are now per-minute: 1,200,000 quota units/min per project; 6,000 quota units/min per user per project; 80,000,000 units/day per project before billing applies. Method costs: messages.send 100, drafts.send 100, messages.get 20, threads.get 40, threads.modify 10, messages.list 5, messages.modify 5, labels.create 5, labels.list 1, history.list 2, watch 100, stop 50, getProfile 1. Max 500 recipients per API-sent message. (Older third-party articles still cite the retired 250 units/user/sec + 1B/day figures.)
- VERIFIED (developers.google.com/identity/protocols/oauth2#expiration): the 7-day refresh-token expiry applies only to OAuth consent screens with user type External and publishing status Testing. Refresh tokens are also invalidated by: user revocation, 6 months of non-use, the user changing their password when the token contains Gmail scopes, and exceeding 100 live refresh tokens per Google account per OAuth client ID. An Internal (Workspace-only) app has no 7-day expiry and needs no Google verification.
- VERIFIED (developers.google.com/identity/protocols/oauth2/service-account): domain-wide delegation is configured by a Workspace super admin at Admin console > Security > Access and data control > API Controls > Domain-wide delegation > Add new, entering the service account's numeric client ID and a comma-delimited scope list. The service account then impersonates support@ via the JWT 'sub' claim (Node googleapis: new google.auth.JWT({..., subject: 'support@domain'})). No refresh token exists to expire, and password changes on support@ don't break it.
- VERIFIED (developers.google.com/workspace/gmail/api/guides/threads): to insert a reply into an existing thread via users.messages.send you must (1) set threadId on the Message resource, (2) set In-Reply-To and References headers per RFC 2822 (In-Reply-To = original Message-ID; References = original References + Message-ID), and (3) the Subject headers must match. Fetch the original's Message-ID/References/Subject with users.messages.get (format=metadata, metadataHeaders=...). The message body goes base64url-encoded in the 'raw' field.
- VERIFIED (developers.google.com/workspace/gmail/api/guides/labels): custom labels via users.labels.create (user-type labels; cannot reuse system label names like INBOX/SPAM); apply/remove via users.messages.modify {addLabelIds:[], removeLabelIds:[]} or users.threads.modify — but threads.modify only touches messages existing at call time. Label management scope: https://www.googleapis.com/auth/gmail.labels.
- VERIFIED (knowledge.workspace.google.com Gmail sending limits KB): Workspace Gmail limits: 2,000 messages/day (500/day for trial accounts; 1,500 for mail merge), 10,000 total recipients/day, 3,000 external recipients/day, 3,000 unique recipients/day (2,000 external; 500 external on trial); exceeding limits suspends sending for up to 24 hours. API sending allows 500 recipients/message vs 100 via SMTP/IMAP. Limits can change without notice.
- VERIFIED (Google Workspace admin docs/KB): deliverability DNS = SPF TXT 'v=spf1 include:_spf.google.com ~all'; DKIM generated at Admin console > Apps > Google Workspace > Gmail > Authenticate email (2048-bit default; publish TXT at google._domainkey.<domain>, then click Start Authentication; propagation up to 48h); DMARC TXT at _dmarc.<domain> e.g. 'v=DMARC1; p=none; rua=mailto:dmarc@<domain>' — Google says have SPF+DKIM authenticating for 48h before enabling DMARC, then tighten p=none → quarantine → reject.
- VERIFIED (Gmail API guides + Workspace alias docs): the Gmail API only operates on real user mailboxes. A Google Group is not a Gmail mailbox and its messages are not reachable via the Gmail API; an alias has no mailbox of its own — mail to the alias lands in the primary user's mailbox and the API authenticates as that user. Sending 'from support@' when it is an alias requires a users.settings.sendAs entry.
- UNVERIFIED (strong recollection, not re-checked in scopes doc): the single scope https://www.googleapis.com/auth/gmail.modify covers all read/compose/send/label operations except permanent deletion, so it can be the only scope granted to the agent; gmail.readonly + gmail.send + gmail.labels is the narrower alternative bundle.
- UNVERIFIED (widely documented behavior): a stored startHistoryId older than roughly a week can be expired, making users.history.list return 404 — handle by falling back to a full users.messages.list resync; also messages arriving into a labeled thread after threads.modify do not inherit the thread's labels, so re-apply state labels on each inbound message.

Gotchas:
- Silent watch death: users.watch expires after at most 7 days with no error or warning on either side — if you use push, a daily renewal job in the ops-service queue is mandatory, and a missed renewal means notifications just stop.
- Push notifications are only wake-up signals: the historyId in the Pub/Sub payload should not be fed directly to history.list — always call users.history.list with your own last-processed historyId, and be ready for 404 (expired historyId) requiring a full resync.
- OAuth-refresh-token path landmines: (1) leaving the consent screen External+Testing kills the token after 7 days — set user type to Internal; (2) changing the support@ password revokes any refresh token carrying Gmail scopes — a routine password rotation would silently break the agent; (3) tokens unused 6 months die (irrelevant for an always-on agent).
- Service-account key is a domain-wide skeleton key: with delegation it can impersonate ANY user in the Workspace for the granted scopes, not just support@ — restrict scopes to Gmail only, store the key in Railway/Fly secrets, and never commit it.
- Google Groups and aliases don't work for an API-driven agent: Groups have no Gmail-API-accessible mailbox at all, and an alias on the owner's account would give the AI agent full read/send access to the owner's personal mailbox.
- A brand-new Workspace tenant is under trial limits (500 messages/day, 500 external unique recipients) until billing is established — fine for support volume but relevant if the sourcing/marketing agents ever send mail from the same tenant.
- Quota math on the new per-minute system: 6,000 units/min/user means at most ~60 messages.send calls/min and threads.get (40 units) is now expensive — prefer messages.get with format=metadata and history.list (2 units) for polling.
- Threading breaks if any of the three conditions is missed — threadId alone is not enough; a changed Subject or missing References/In-Reply-To makes Gmail (and especially other clients like Outlook) start a new conversation.
- threads.modify labels only existing messages; each new inbound customer reply arrives unlabeled and must have the ticket-state label re-applied by the ingest job.
- DMARC ordering: publish SPF and DKIM and let them authenticate for ~48h before adding the DMARC record; start at p=none with rua reporting, and only move to quarantine/reject after reports look clean — going straight to p=reject can nuke your own replies.
- Exceeding Workspace sending limits suspends the mailbox's sending for up to 24 hours — an agent retry loop that re-sends on failure could dig this hole deeper; make sends idempotent through the job queue.

Recommendations:
- Create a dedicated Workspace user support@<domain> (one extra paid seat). This isolates the agent's credentials to the support mailbox only, gives real Gmail API access, and keeps the owner's own mailbox out of the agent's reach. Do not use a Group or an alias on the owner's account.
- Authenticate with a service account + domain-wide delegation scoped to a single Gmail scope (gmail.modify): create the SA in the GCP project, enable delegation, authorize its numeric client ID in Admin console (Security > API Controls > Domain-wide delegation), and impersonate support@ via the JWT subject. This is the most durable headless option — no consent flow to re-run, no refresh token to expire, immune to password changes. Fallback option if you prefer no domain-wide key: an Internal OAuth app with a one-time consent for support@ and the refresh token in Railway/Fly secrets (never expires under Internal, but dies on password change).
- GCP setup checklist: one project; enable Gmail API (plus Cloud Pub/Sub API only if/when you adopt push); create the service account and key; authorize delegation in Admin console with scope https://www.googleapis.com/auth/gmail.modify.
- Receive mail by polling first: a queue job every 30–60s calling users.history.list (2 quota units) with the stored historyId, seeded via users.getProfile. That is ~4 units/min against a 6,000 units/min/user budget, has zero extra infrastructure, and suits an always-on ops service. Upgrade to users.watch + Pub/Sub push later if sub-minute latency matters — and if you do, add a daily watch-renewal cron and grant gmail-api-push@system.gserviceaccount.com Publisher on the topic.
- Reply flow: users.messages.get (format=metadata, metadataHeaders=Message-ID,References,Subject,From) on the inbound message → build RFC 2822 raw reply with In-Reply-To, References, matching Subject (Re: prefix) → users.messages.send with {raw, threadId}. Route outbound sends through the existing job queue with idempotency keys so retries never double-send.
- Ticket state: keep Postgres as the source of truth and mirror state into Gmail labels for human visibility — users.labels.create once at boot (e.g. DogeBuddy/New, DogeBuddy/AwaitingApproval, DogeBuddy/WaitingOnCustomer, DogeBuddy/Escalated, DogeBuddy/Resolved), then users.messages.modify addLabelIds/removeLabelIds per message (re-applying on every new inbound message in a thread).
- DNS before first send: MX records for Google, SPF 'v=spf1 include:_spf.google.com ~all' (merge into one SPF record with Shopify's include when storefront email is added — a domain may have only one SPF TXT), 2048-bit DKIM activated in Admin console, DMARC starting at 'v=DMARC1; p=none; rua=...' and tightened after reports are clean. Verify with Google Admin Toolbox Check MX.
- Budget note: at support-scale volume (tens of emails/day) you will never approach either the API quotas or the 2,000/day Workspace sending limit; no quota-increase requests needed.

Uncaught handler exceptions become error tool-results (agent loop continues); return `isError: true` to compose the message Claude reads. `annotations: { readOnlyHint: true }` allows parallel calls. Tool search is ON by default and defers SDK MCP tool schemas; `alwaysLoad: true` pins a schema in context.
- VERIFIED — structured output: `options.outputFormat = { type: 'json_schema', schema }` (JSON Schema draft-07 only; from Zod use `z.toJSONSchema(Schema, { target: 'draft-7' })`). Agent uses any tools, then final result message carries validated JSON at `message.structured_output` when `message.type === 'result' && message.subtype === 'success'`. SDK validates and re-prompts on mismatch; failure surfaces as result subtype `error_max_structured_output_retries`. A `success` result can still lack `structured_output` — treat that as failure too.
- VERIFIED — sessions: session_id arrives in the init system message; resume with `options.resume: sessionId` (plus `forkSession`, `resumeSessionAt`, explicit `sessionId`, `persistSession`, `continue`). Helper fns: `listSessions()`, `getSessionMessages()`, `getSessionInfo()`, `renameSession()`, `tagSession()`. Transcripts live as JSONL under `~/.claude/projects/` (or `CLAUDE_CONFIG_DIR`) — lost on container restart; a `SessionStore` adapter (reference impls for S3, Redis, Postgres) mirrors transcripts to durable storage (local disk stays authoritative; failed mirror batches emit `{type:'system', subtype:'mirror_error'}`).
- VERIFIED — cost tracking: final result message has `total_cost_usd`, cumulative `usage` (input_tokens, output_tokens, cache_creation_input_tokens, cache_read_input_tokens), and `modelUsage` — a per-model map with `costUSD`, `inputTokens`, `outputTokens`, `cacheReadInputTokens`, `cacheCreationInputTokens`. `usage` EXCLUDES subagent tokens; `total_cost_usd` and `modelUsage` include them. Per-step usage on assistant messages must be deduped by `message.message.id` (parallel tool calls share an id). `total_cost_usd` is a client-side estimate from a bundled price table — NOT billing data; authoritative billing is the Usage & Cost API / Console. Prompt caching is automatic (5-min TTL; `ENABLE_PROMPT_CACHING_1H=1` env for 1h TTL).
- VERIFIED — cancellation: (1) `options.abortController` + `controller.abort()`; (2) `await q.interrupt()` in streaming-input mode (returns `{still_queued, cancelled}` message UUIDs, v2.1.205+); (3) `q.close()` force-kills and cleans up. There is NO built-in wall-clock session timeout — bound runs with `maxTurns` + `maxBudgetUsd` + your own timer calling abort().
- VERIFIED (code.claude.com/docs/en/agent-sdk/hosting): one session = one subprocess; N concurrent jobs = N `claude` subprocesses. Sizing guidance: ~1 GiB RAM, 1 CPU, 5 GiB disk per agent as a starting floor; agents-per-host = (host RAM − overhead) / measured per-session peak RSS. Pass a distinct `cwd` per job for filesystem isolation. Isolation kit for shared hosts: `settingSources: []`, `CLAUDE_CODE_DISABLE_AUTO_MEMORY=1`, per-tenant `CLAUDE_CONFIG_DIR`, per-job cwd. `startup()` pre-warms a subprocess for latency. OTEL export via env (`CLAUDE_CODE_ENABLE_TELEMETRY=1`, OTLP exporters) gives spans/metrics/logs per query.
- VERIFIED — streaming/audit: iterating the query() generator yields every SDKMessage (assistant turns incl. tool_use blocks, user tool results, system, result) — persist these per job for an audit trail; `includePartialMessages: true` adds token-level partial events; hooks (PreToolUse/PostToolUse etc. via `options.hooks`) can log or veto individual tool calls in-process.
- VERIFIED (platform.claude.com models overview, fetched 2026-08-09) — current model IDs + pricing per MTok: `claude-opus-5` $5/$25 (1M ctx, 128K out); `claude-sonnet-5` $3/$15 with INTRO pricing $2/$10 through 2026-08-31 (1M ctx, 128K out); `claude-haiku-4-5` $1/$5 (200K ctx, 64K out, fastest; supports extended thinking but NOT adaptive thinking); `claude-fable-5` $10/$50 (top-end, overkill here); legacy `claude-sonnet-4-6` $3/$15 still active. Cache reads ~0.1x input price; cache writes 1.25x (5m) / 2x (1h). Batch API is 50% off (relevant for scoring/batch classification, not agent runs).

Per-workflow verdict for Doge Buddy: fulfillment = NO LLM at all (deterministic webhook→CJ purchase→tracking sync; plain TypeScript + BullMQ); scoring = plain code over Postgres metrics plus at most ONE Messages API call with structured outputs (`client.messages.parse` / `output_config.format`) for the swap/keep judgment; sourcing agent = Agent SDK fit (built-in WebSearch/WebFetch + custom CJ tools + structured_output listing draft); support agent = Agent SDK fit (multi-turn, sessions/resume per email thread, custom Gmail/Shopify/CJ tools, `tools: []` to strip filesystem/Bash built-ins); email triage/classification = single `claude-haiku-4-5` Messages API call, no agent.

Gotchas:
- ToS: Anthropic does not allow third-party products built on the Agent SDK to offer claude.ai login or claude.ai rate limits — API key auth (ANTHROPIC_API_KEY) is required for a commercial product like Doge Buddy. Commercial Terms of Service govern SDK use; branding rules prohibit calling your agent 'Claude Code'.
- Railway/Fly deploys replace containers: session transcripts, CLAUDE.md memory, and working-dir artifacts live on local disk by default and are LOST on redeploy/restart. Any resumable session (e.g. a support email thread) requires a SessionStore adapter (Postgres fits your stack) — it mirrors transcripts only, not working-dir files.
- `total_cost_usd`/`costUSD` are client-side estimates from a build-time price table — they drift when pricing changes or the SDK doesn't know a model. Fine for dashboards/budget caps; never bill from them (use the Usage & Cost API).
- Memory sizing: each concurrent query() is a full `claude` CLI subprocess (~1 GiB+ RSS, grows with session length). A 2 GB Railway/Fly instance realistically supports ~1-2 concurrent agent jobs; set BullMQ worker concurrency accordingly and measure peak RSS. Known limitation: memory grows over long sessions — cap length or recycle.
- No built-in wall-clock timeout on a session — an agent job can run indefinitely. Always set maxTurns, consider maxBudgetUsd, and wire a queue-level timeout to abortController.abort(). Subagents also lack a total-runtime deadline (cap via per-agent maxTurns).
- In TypeScript, `options.env` REPLACES the subprocess environment — spread `...process.env` or the subprocess loses PATH and ANTHROPIC_API_KEY.
- query() THROWS after yielding an error result message — wrap iteration in try/catch inside the job handler or the worker crashes; cost data on the error result is still valid and should be recorded before the throw.
- Structured outputs: schema must be JSON Schema draft-07 (Zod defaults to 2020-12 — pass `target: 'draft-7'` or the run fails at startup on SDK ≥2.1.205); a `success` result can still lack structured_output; `format:` keywords are annotation-only (not enforced).
- By default the agent loads filesystem settings, skills, and CLAUDE.md from cwd and ~/.claude — for a server-side ops service, pass `settingSources: []` and `CLAUDE_CODE_DISABLE_AUTO_MEMORY=1` for deterministic, reproducible agent config defined entirely in code.
- `permissionMode: 'bypassPermissions'` additionally requires `allowDangerouslySkipPermissions: true` — avoid it; prefer `tools: []` + explicit `allowedTools` allowlist of your own mcp__ tools.
- claude-haiku-4-5 has a 200K context, 64K max output, and no adaptive thinking — fine for triage classification, wrong choice as an Agent SDK main-loop model for complex tasks.
- Sonnet 5 intro pricing ($2/$10) ends 2026-08-31 — three weeks from now; budget at the $3/$15 sticker.
- Large parallel-subagent fanouts from one session can hit API rate limits — batch work instead of one wide dispatch.
- Cold-start latency: first query() pays subprocess spawn cost; use startup() to pre-warm in a long-lived worker.
- The bundled CLI binary is pinned to the SDK package version — updating the npm package is how you update the harness; take patch releases freely, review CHANGELOG before minors.

## trends
For a weekly, ToS-compliant dog-product trend agent in 2026, the practical stack is: (1) CJ Dropshipping's own API trending list (official, already your first supplier, zero extra legal risk, directly actionable), (2) Google Trends as a validation layer — apply to Google's official alpha API now and bridge with a paid provider (SerpApi/DataForSEO) since pytrends and the npm google-trends-api are dead, and (3) the agent's own web search as a free qualitative baseline. TikTok Creative Center, Amazon Best Sellers, and Reddit all turned out to be poor fits for compliant automation: TikTok's official APIs exclude commercial users, Amazon killed PA-API 5.0 in favor of a Creators API that requires 10 qualifying affiliate sales/30 days, and Reddit's free tier is non-commercial with commercial approval being slow and expensive.

Key facts:
- VERIFIED (a): CJ Dropshipping's API v2 docs (developers.cjdropshipping.com/en/api/api2/api/product.html) expose trending products: the Product List endpoint (GET /api2.0/v1/product/list) has a searchType parameter with 0=All products, 2=Trending Products, 21=Trending Products (View More), plus orderBy=1 to sort by listing count (a popularity proxy). listV2 adds richer filters (category, price, country/US-warehouse inventory) but no explicit bestseller flag.
- VERIFIED (a): CJ API rate limit for free/v1 users is 1,000 requests/day, max 3 users per IP — trivially sufficient for a weekly sourcing run.

Third-party Apify scrapers exist but violate TikTok's ToS and are brittle.

Gotchas:
- Amazon is effectively closed to you at launch: PA-API 5.0 returns 403s for non-migrated apps, the Creators API needs 10 qualifying AFFILIATE sales in the past 30 days (a dropshipping store generates none), and scraping Best Sellers pages directly violates Amazon's Conditions of Use. - Do not build on pytrends or npm google-trends-api — both are dead. - Google's official Trends API alpha is application-gated with no guaranteed or scheduled GA — apply early but design the agent so the Trends adapter is swappable (alpha ↔ SerpApi/DataForSEO).

Recommendations:

(3) BASELINE — the agent's own WebSearch tool: weekly qualitative sweep ('trending dog products', 'viral dog toy TikTok', pet-industry blogs) summarized by the agent into candidate keywords that feed signal (2). (4) MANUAL — a 'TikTok Top Products' checklist item in the owner's weekly approval email: 10 minutes in Creative Center (Pet Supplies, US, last 7 days), typed or pasted into the admin dashboard as owner-supplied signal.
- Architect this as a SourcingSignal adapter interface mirroring your SupplierAdapter pattern: each adapter returns normalized {keyword/product, source, score, evidence_url, fetched_at} rows into Postgres, so the scoring agent consumes signals uniformly and adapters (official Trends alpha vs SerpApi, future Reddit-with-approval) are swappable without touching agent logic.
- Have the sourcing agent triangulate rather than trust any one feed: a candidate needs (a) presence on CJ trending or web-search sweep AND (b) rising/stable Google Trends interest in the US before it becomes a listing proposal for owner approval.
- Skip Amazon, Reddit, and TikTok automation at launch.
